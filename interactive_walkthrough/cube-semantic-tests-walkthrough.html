    ✅ 312 dbt tests passed

    Every one of these problems sits above the tables. The data in BigQuery was fine. What broke was the layer that turns tables into answers: joins, access rules, measure definitions and cached rollups. dbt can't test that layer, so cube-semantic-tests does.

    🧪 dbt tests see

    Columns are unique and not null, relationships hold, values are accepted. All inside BigQuery tables.

    🔍 This suite sees

    The views people query, who can see which rows, the SQL Cube generates, the numbers Cube returns, and the rollups in Cube Store.

    👥 People see

    Looker, apps and AI agents all query the same Cube views, so one mistake there reaches all of them at once.

    🍽️🕵️

    Think of it as mystery diners for your data

    Your semantic layer is a restaurant. dbt tests inspect the ingredients when they're delivered. This framework sends mystery diners who order real dishes as real customers and check that what arrives at the table is right. Click a tile to see what each part maps to.

    The short version: order as real customers, never with the manager's master key; check the menu and the locks before cooking anything; then taste the food and weigh it against a recipe someone else wrote.

    Cube Cloud vs BigQuery: who answers what

    Here is the restaurant for real. The suite talks to four things. Pick a call to trace its path. The key idea: Cube's answers are compared against BigQuery queried directly, bypassing Cube, so the two are independent.

    How it runs in GitHub Actions

    ci/github-actions.yml has two paths. Pull requests get the cheap gate against the branch's staging environment. After the production dbt run, Airflow fires a repository_dispatch and the full suite runs against production.

    Folders and test tiers

    Tests are grouped into tiers with pytest markers. Each tier needs more infrastructure and costs more than the one before, so cheap checks run often and expensive ones run once the data has loaded.

    semtest/          client code: Cube REST + Control Plane, BigQuery runner, /meta helpers, comparison
  cube.py           CubeClient (mints JWTs, /meta, /v1/sql, /v1/load, rows_all) + ControlPlane
  bq.py             BigQueryRunner (bytes-billed cap, job labels)
  meta.py           read /meta: views, members, aliasMember, additivity
  compare.py        match Cube rows to BigQuery rows within tolerance
  sqlcheck.py       read row-filter predicates out of generated SQL      new
  freshness.py      rollup freshness at the rollup's own granularity      new
config/           EDIT THESE: suite.yml, personas.yml, parity_cases.yml, rollup_cases.yml
tests/contract/   compile, storefront, governance, access   (no BigQuery cost)
tests/data/       smoke, row values, fan-out, parity, rollups (executes through Cube)
tests/unit/       the framework's own tests against a fake Cube   new
scripts/          lint_model.py, wait_for_rollups.py
ci/               example GitHub Actions workflow

    Five design rules you'll see everywhere

    RuleWhat it means in the code
    No admin fallbackEvery Cube call runs as a named persona with a freshly signed, short-lived JWT. CubeClient has no "default token" path.
    Targets come from /metaFan-out pairs and row-filter targets are discovered from Cube's metadata, so a newly published view is covered without editing a list.
    Config, not codeViews, personas, golden numbers and rollups live in config/*.yml. The tests themselves never need editing for a new view.
    Independent referencesGolden numbers from finance come first. Reference SQL should be written by someone other than the measure's author.
    Bounded costShort date windows, a pair cap on fan-out, and a bytes-billed cap plus labels on every BigQuery job.

    Everything project-specific lives in config/

    semtest/config.py loads four YAML files and a .env. Pick a file, then click a key on the right to highlight it and see which code reads it.

    The config folder can be moved with SEMTEST_CONFIG_DIR (relative paths resolve from the suite root, and a folder that doesn't exist is an error). This is one of the recent fixes. See step 11.

    Every call runs as a persona

    A persona is a test identity. Its claims become the JWT payload, which Cube turns into the security context that context_to_groups and access_policy rules read. CubeClient.mint_token() signs a new HS256 token on every request, with iat and a 15-minute exp.

    Data tier: queries actually run
    
  
    These execute through Cube, so BigQuery is billed. Each one is bounded by smoke_date_range to keep cost down.
    
  
    
    
    Smoke
    One batched query per view with every measure. On failure, each measure is retried alone to name the culprit. A measure pointing at a missing column compiles fine and only fails here. Every time dimension is also sliced by month.
    
    
    Row values
    The contract tier proved the predicate is in the SQL. This proves the rows that come back hold only the persona's allowed values, which also catches a join that reintroduces rows. Uses rows_all so a cut-off list can't hide a leak.
    
    
    Fan-out
    For each additive measure and each dimension reached through a join (different aliasMember cube), the grand total must equal the sum of the grouped totals. Try it below.

    Parity: is the number right?
    
  
    Each case in parity_cases.yml sets exactly one reference: a golden expected number with a source (strongest, because the measure's author didn't produce it), or bigquery_sql run directly against BigQuery. A contract-tier check, test_case_is_well_formed, enforces that every case has an owner and a known persona.
    
  
    
    
    Golden number
    The query must return one row; Cube's value must be within abs_tol/rel_tol of expected.
    Cube=4,209,999.40 golden=4,210,000.00  abs_tol=1.00  → pass
    
    
    BigQuery reference
    compare_rowsets matches rows on keys (Cube member → BQ column), then compares values. It reports rows missing on either side and every value outside tolerance.
    
  
    
  
    Case types in the example config: a golden month total, by-state-by-month, a trailing-12-month window, prior year (time_shift), and row-level security checked numerically (NSW analyst's total must equal BigQuery's NSW total, not merely be smaller).

    Four bugs that let broken things pass
    
  
    Each was a false pass or a misleading failure. Each fix comes with unit tests in tests/unit/ that run against a fake Cube with no network or credentials (pytest -m unit), and CI now runs them before the contract tier.
    
  
    
    
  
    

  
    
    
    
      
    Before
    The freshness test asked for the latest day. A monthly rollup can't answer a daily query, so Cube sent it to BigQuery, and the test compared BigQuery with itself. A rollup stuck in August passed.
    
      
    After
    semtest/freshness.py asks at the rollup's granularity, fails unless usedPreAggregations names the rollup, compares periods (the rollup must hold the period containing source latest minus max_lag_days), and optionally checks max_refresh_age_hours to catch staleness within the current month.
    
    
    
    
    Try it in the freshness simulator in step 11. Unit tests: test_rollup_freshness.py (stale rollup now fails, source-served query fails, lag across a month boundary allowed, refresh age without a timestamp fails rather than passes).
    
  
    

  
    
    
    
      
    Before
    The config folder was read from SEMTEST_CONFIG_DIR once, at import time, before .env was loaded. A value set in .env was silently ignored and the example config ran instead.
    
      
    After
    config_dir() loads .env and then resolves the folder on every call. The real environment wins over .env, a relative path resolves from the suite root, and a missing folder raises ConfigError instead of quietly giving an empty config.

    Before
    Queries were sent with no limit, so Cube silently applied its default of 10,000 rows. A large result came back cut off and was compared as if complete, showing up as "missing from Cube" parity rows or a fan-out "SHRANK (rows dropped by join)".
    
      
    After
    CubeClient.rows_all() sets limit to suite.yml › row_limit (match your CUBEJS_DB_QUERY_LIMIT, 50,000 by default). A result that fills it raises TruncatedResult, which says plainly the result was probably cut off. A query that sets its own limit is treated as a deliberate top-N.

    Before
    The row-filter check looked for each allowed value anywhere in the SQL text or params. A value like 1 matched LIMIT 10000; NSW on the wrong column passed; a filter that also let VIC through passed.
    
      
    After
    semtest/sqlcheck.py finds = / IN (…) predicates on the filter column (any quoting, optional table qualifier), resolves ?, $n and literal values, and requires exactly the allowed set. An unrecognised shape fails loudly rather than passing.

    Check these against your deployment
    
  
    The suite was exercised against a local fake of Cube's REST API with planted bugs, not a live Cube Cloud deployment.
    
  
    
    
    AssumptionWhy it matters
    
    
    Token claim namescheck_auth / context_to_groups must read the claims in personas.yml. With Cube Cloud SSO user attributes, personas need real test users.
    
    
    /meta fieldsEntries carry type: view|cube; view members carry aliasMember. Without it, fan-out tests skip.
    
    
    Pre-aggregation fields/v1/sql returns preAggregations and /v1/load returns usedPreAggregations; names are matched as substrings.
    
    
    Staging URL patternCopy a real branch URL into CUBE_STAGING_API_URL_TEMPLATE.
    
    
    Time zonesEach Cube query's timezone matches how the reference SQL buckets dates.
    
    
    CostFan-out is two queries per pair; every reference query is capped by BQ_MAX_BYTES_BILLED.
